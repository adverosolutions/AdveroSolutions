# Sales demonstration screen contract

The prospect already knows software can solve the problem. The walkthrough
needs to show their specific input, the important mechanism, and a useful
result. A plausible-looking interface is insufficient when it is the wrong
product or the workflow could not behave that way.

## Recording sequence

Target a two-minute primary route, with optional detail available when useful:

| Beat | Approximate time | Visible evidence |
| --- | --- | --- |
| Personal opening | 0–10 seconds | Named business/problem, approved prebuilt caption, one concrete outcome |
| Mechanism | 10–35 seconds | The correct native workflow, skill, agent, IDE or configuration surface |
| Result | 35–90 seconds | Representative input becomes the promised output in the actual destination UI |
| Important exception | 90–105 seconds | One relevant missing-field, reply, duplicate or validation case |
| Goal and close | 105–120 seconds | Clearly labeled intended metric and a prominent 15-minute call CTA |

These are editing targets, not timers. The presenter controls navigation.
Optional chapters must not hide proof required by the original post. The native
workflow remains available when it adds expertise, but assistant and IDE jobs
must not be forced into the existing schema's workflow-first canvas. They need
their own native scene types before production resumes.

## Presentation and native software

Keep Lorenzo's approved outer colors, Inter typography, opening caption and
blue closing CTA. Match the real software's own colors, type, density and
components inside its native frame. Do not apply the deck's generic blue CRM
styling to every application. Do not invent sidebars, tabs, approval buttons,
record fields or node types to make the sample fit the existing renderer.

Keep narration notes in presentation chrome. Do not insert explanatory cards
inside a native application where the application would not have those cards.
Use a controlled native viewport with readable text; pan a larger canvas inside
its frame or show a coherent subsystem. Do not shrink an entire automation until
its labels become unreadable. A reference screenshot shown as a reference is not
a personalized working demonstration.

## Sample and animation behavior

Every scene must have useful visible content on entry. The presenter should be
able to begin talking immediately and finish the beat without waiting on a
timer. Use controlled sample state, with Replay and Show result embedded next
to the actual demo. Nothing auto-advances to the next chapter.

One consistent sample identity runs through all screens: names, email/phone,
record IDs, opportunity values, dates, statuses and totals. A requested message
appears in the correct thread/composer view, a pipeline change moves the actual
sample card, and a document workflow shows readable source-linked output.
No accidental blank CRM/confirmation page, zero-value deal or unrelated toast.

Replay resets only the active scene, handles rapid repeated clicks, and reaches
the same useful final state. Navigation cancels obsolete scene timers. Reduced
motion produces a useful settled state. Smooth scrolling must not depend on a
sticky demo block jumping between sections. Mobile overflow must be contained
without making the desktop recording UI tiny.

## Native capability and proof

Use actual node/module/action families and their real semantics. In n8n, AI
cluster/subnode connections need their typed ports. In Make, multiple router
routes can match, and filters belong to the correct route. In GHL, a reply
handling pattern must use supported settings/triggers rather than an invented
node. A job asking for GHL-native automation should show that native builder.

Output takes place where the user would find it: CRM record, conversation,
spreadsheet, document, agent artifact, native run inspector or working preview.
Show human review through the actual document/chat/task mechanism; do not invent
a vendor approval dashboard. Show goals as goals, sample values as sample values,
and achieved performance only when verified. Do not add a fake JSON download or
claim a native import/snapshot was tested without the actual artifact/evidence.

## Acceptance packet

One packet per native template contains product/surface/version/theme, current
full-screen and detail references with provenance, the implemented screen/state
map, a same-viewport reference-versus-render comparison, replay/navigation/data
checks, and the exact reviewed source/page hashes. The independent reviewer
must reject a wrong product surface even when all technical tests pass.

Job generation starts after that template is accepted. Researching a new
product and building its adapter belong to template maintenance, with the
recording queue kept clear of unfinished native screens.

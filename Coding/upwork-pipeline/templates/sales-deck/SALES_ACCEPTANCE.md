# Sales walkthrough acceptance — applies to every future generation

This is a blocking requirement from Lorenzo (19 October 2026), alongside native
visual fidelity. A technically valid or attractive page can still fail the pitch.

A 1–3 minute Upwork Loom must establish the client’s problem, show the relevant
workflow/setup, visibly demonstrate its useful result, and ask for a reply leading
to a 15-minute call. Keep the approved colors, opening, typography and closing CTA.

Before building, write a short private scene map: each stop’s purpose, new fact,
visible evidence and narration time. Use 2–3 native demonstration stops where the
job permits; add a stop only for a separate requirement/result. Cover and closing
are separate. Optional technical context must not hide the main result in Quick.
Do not add empty Project pages, repeated canvases or several copies of a final-node
inspector to make a deck longer. Detailed can expose controls on the same screen.

For every scene, answer:
- What new buyer-relevant fact appears here? If it repeats the last stop, merge it.
- Can Lorenzo point at the result without reading JSON or opening a hidden pane?
- Does the depicted workflow actually explain this result? Show separate triggers
  when required; do not jump from an acknowledgement to a confirmed booking.
- Do identity, owner, amounts, status, time and messages agree across the story?
- Does the narration explain the business effect rather than list interface parts?

Use tool/job-specific directional goals in the closing; never fabricated measured
uplifts. The CTA must explicitly request the reply and the 15-minute call. Keep
setup caveats and reference gaps in private evidence, while marking sample data
once in the presentation. Do not misrepresent simulated output as a live delivery.

Main checks all routes and captures cover, every distinct scene and close. Verify
immediate useful entry, Replay, Show result, navigation, notes, Present and reduced
motion. Compare actual native screens with sourced references. Exact duplicate
native proof payloads are compiler errors; semantic repetition and unexplained
workflow/result jumps require human/model review and cannot be proved by this lint.

### Spoken clarity is required

Read every heading, caption, metric and CTA aloud in presentation order, joining split title/accent text. Each line must have an obvious meaning without decoding developer shorthand. “Agree the product. Test one journey.” fails; “Let's map out your first feature” states the action. Talking points must explain the visible example in ordinary spoken sentences. Preserve exact native control labels and factual details; put their plain-language explanation alongside them. Clarity failures block recording approval even when the screen is attractive and technically correct.

# Outcome sync (proposals.csv viewed / replied / interviewed / hired, plus boosted)

The script cannot call Upwork. A Claude session pulls the JSON with read-only Upwork MCP tools, saves it under `<scratchpad>/`, and `sync_outcomes.py` ingests the files. org_uid `2081884703335585732`.

1. Proposals: `list_freelancer_proposals action=list` once per status `Accepted, Activated, Offered, Hired, Declined, Archived, Withdrawn`, with `params {"status": "<status>", "limit": 10}` (`status`, `limit` and `cursor` always inside `params`; the default status is Accepted). Page with `params.cursor` = the previous `next_cursor`. **An empty page is NOT the end**: the connector drops other statuses from each page, so a page can have no edges and more behind it. Stop only when `next_cursor` comes back unchanged, or when its offset (base64-decode it: `{"Active":"25",...}`) has reached the response's `totalCount`. Save every response, raw, as one JSON list to `<scratchpad>/proposals.json`.
2. Replies: `list_freelancer_proposals action=get_room params {"proposal_id": ...}` for every proposal that matches a log row and is `Accepted`, `Declined`, `Archived` or `Withdrawn`. Save `{"<proposal_id>": <response>}` to `<scratchpad>/rooms.json`; save a NOT_FOUND error as `{"error_code": "NOT_FOUND", "status": "error"}`. NOT_FOUND means the client never messaged; only on a closed proposal does it write replied/interviewed "no".
3. Views: `list_freelancer_proposals action=get params {"id": "<proposal_id>"}` for every matched proposal that is still open (`Accepted`). The id must be the proposal id: a job id silently returns a job response with no insights. Save `{"<proposal_id>": <response>}` to `<scratchpad>/insights.json` (only `insights` is read; the cover letter may be dropped). The counts are per job and may not include our proposal (Upwork: "Averages describe the other applicants for this job"), so they never write viewed yes. On an open proposal (`Accepted`, `Activated`, `Offered`), `proposals_opened`, `messaged` and `shortlisted` all 0 → viewed no, which a later sync upgrades to yes once a reply, interview or hire shows a view. Anything else stays blank, and closed proposals (`Archived`, `Withdrawn`, `Declined`) get nothing from insights.
4. Hires: `list_contracts action=search params {}` → `<scratchpad>/contracts.json`. Contracts have no job id: one applies only if exactly one proposal has its title, it starts on/after that proposal and the proposal is not Declined/Withdrawn/Archived. The rest print as unmatched contracts.
5. Preview (writes nothing):
   ```
   cd /Users/lorenzovillarreal/Desktop/AdveroSolutions/Coding/upwork-pipeline && python3 sync_outcomes.py --proposals <scratchpad>/proposals.json --rooms <scratchpad>/rooms.json --insights <scratchpad>/insights.json --contracts <scratchpad>/contracts.json --fill-boosted --dry-run
   ```
   The result goes to a temp copy and you get a diff. A "WARNING: skipped malformed row/record" (wrong or ambiguous field count, a quote left open past its line, or unparseable) is left untouched and out of the rates: fix it by hand; its proposal is listed under "belong to a skipped row". "AMBIGUOUS" means several URL-less rows share a proposal title, so none is updated: add the job_url to the right row. "UNMATCHED: row N" means a URL-less row's exact title is a job another row already claims: add its job_url. "unmatched rows" counts log rows with no fetched proposal (a proposal never submitted, or one the connector did not return).
6. Apply: same command without `--dry-run`, and only once no finalize or batch run is writing proposals.csv. Values only move up (empty→yes/no, no→yes); `--fill-boosted` only fills a blank boosted cell. Only changed rows are rewritten, the result is verified before it replaces the file, the run aborts if anything else wrote proposals.csv meanwhile, and the previous file is kept as `proposals.csv.bak`.
7. Rates: `python3 sync_outcomes.py --report` prints view, reply, interview and hire rates (yes / rows, with counts) by `platform` and `opener_variant`. Skipped malformed rows are never counted; a "not counted" line names them. With `--dry-run` it is labelled "(dry run, not written)".
8. Limits: Upwork does not show "viewed" per proposal; besides step 3 it is inferred from a reply, interview, hire or a client decline. `Activated` (label "Invitation accepted") = client opened an interview = replied + interviewed. hired "no" = proposal Declined/Archived/Withdrawn.
9. Never call send_message, manage_proposals, manage_meetings, submit_milestones, update_profile, boost_profile or respond_to_offer for this. The sync is read-only on Upwork.
10. Prefix risk: a row with no job_url is matched by title, and a truncated title by a unique 15+ character prefix; if its own proposal was not fetched, that prefix can match a different job. Always log the job_url.

## Apply-time columns (finalize)

`upwork_gen.finalize` fills these when it appends a row (`upwork_gen/apply_meta.py`); missing data leaves the column blank and never stops the log:
- `job_created_utc`: `--posted <ISO UTC time>`, else a `created_utc: <ISO time>` line in jd.txt (`find_jobs action=search` returns `created_date` per job; `find_jobs action=get` and `find_saved_jobs` do not), else the date in "Posted YYYY-MM-DD" ("Posted about ..." is skipped).
- `age_hours_at_apply`: hours from job_created_utc to the finalize run, only when job_created_utc has a time of day.
- `connects`: `--connects N`, else "Connects to apply: N" in jd.txt. This is the cost to apply; a boost bid is extra (list responses carry it as `terms.connectsBid`).
- `boosted`: `--boosted yes|no`; left blank otherwise, and step 6 with `--fill-boosted` fills it from Upwork.

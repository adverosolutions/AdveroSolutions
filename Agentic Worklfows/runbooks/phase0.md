# Runbook: Phase 0 Instantly change-set

## Purpose

Stage every Phase 0 change to the six live Instantly campaigns as a reviewable change-set (blueprint Section 7 Phase 0, M3 copy hygiene and spintax, part of A7), so Lorenzo can read the exact diff before anything touches production. Nothing in this change-set is applied by default; the apply path is refused unless `MODE=live` and `ALLOW_LIVE_WRITES=1` are both set and one campaign key is named.

What is staged, all under `changesets/instantly_phase0/`:

| File | Content |
|---|---|
| `lead_labels.json` | 11 custom lead labels (S1 taxonomy) with descriptions drawn from the recorded replies, created with `use_with_ai: false` (R9) |
| `campaign_settings.json` | per campaign: `pl_value` 6000 (reactivation) / 7500 (outbound), `stop_on_auto_reply` false, tracking off (the last three are already so), plus the shared `campaign_schedule` 07:00-19:00 America/Chicago Mon-Fri (live is 07:00-19:00 America/Detroit with Saturday on, i.e. 06:00 CT and weekends); note that AI Smart Pause is UI-only |
| `sequences/<campaign_key>.json` | full 3-step sequences in Instantly shape: step 1 variants A (live copy, defects fixed) and B (new angle), step 2 as today, step 3 on day 7 as a new thread with a different proof point; 3 to 5 spin points per email |
| `openers_<niche>.md` | 12 hand-written opener variants per segment (the spin options are drawn from these) |
| `subsequence_interested_quiet.json` | the ONE Interested-quiet object: the copy Lorenzo reviews AND the exact `POST /subsequences` body `changesets/instantly_subsequences/apply_subsequences.py` sends (`_meta` stripped). D1/D3/D7 by `pre_delay` 1 then delays 2 and 4; `conditions` present carrying no trigger, with the empty-set semantics UNVERIFIED and checked by hand at go-live step 10. Leads are enrolled by an explicit move, one lead per call, and only when slots were offered and went unanswered. The cadence agent (A2) owns the live fresh-slot version |
| `build_sequences.py` | copy source of truth; regenerates the JSON files (`--check` fails when they are stale) |
| `phase0_lib.py` | validator, HTML/text conversion, unified diff, settings delta |
| `apply_instantly_phase0.py` | dry-run (default) / guarded apply / restore / labels |

Rollback points follow `changesets/rollback.py`, shared by every script that PATCHes a campaign. An apply writes the before-image as `changesets/backups/phase0_<campaign_id>_<ts>.preapply.json` immediately before its PATCH, and settles it before the run ends: in live mode it always becomes the rollback point `phase0_<campaign_id>_<ts>.json` (no suffix), whether the PATCH was verified, acknowledged but not visible on a re-read, or raised. A PATCH that raised is never settled as `.not_applied`, because a 504 can land after the re-read that showed nothing; the point's `outcome` says `landed_after_error`, `unchanged_at_reread` or `unknown_after_error`, and a restore of a point whose write never landed finds nothing to change and sends nothing. `.not_applied.json` is written only in shadow, where no PATCH was sent. So a `.preapply.json` found on disk means the process died mid-PATCH, **not** that nothing was written: compare it with the live campaign before doing anything. Every file carries a `_rollback_point` block (script, campaign id and key, kind, the fields the PATCH changed, the `after` image the PATCH set, the outcome), and `--restore` refuses any file whose block does not match. A re-apply of a campaign that already matches the staged copy sends nothing and writes nothing, so it can never replace the rollback point. A dry-run writes its copy under `.tmp/changeset_dryruns/phase0/` as `.dryrun.json` and never touches `changesets/backups/`; a restore writes `.prerestore.json` of the state it is about to overwrite, which is not itself restorable (to undo a restore, re-run the apply). Files from before 2026-09-22 have no `_rollback_point` block and are refused. The subsequence applier writes its pre-create copy into the same directory as `subsequences_before_<ts>.json` (it used to write one directory deeper, into `changesets/instantly_subsequences/backups/`, where nobody following this runbook would look; older files may still be there). Drafts for Lorenzo's hand-sent messages are in `changesets/drafts/`. Hand steps (Zoom, A2P, GHL token, ntfy, domains, UI toggles, Upwork) are in `changesets/PHASE0_MANUAL_CHECKLIST.md`.

## Rollback

Each apply leaves one rollback point per campaign: the complete campaign object as it was read immediately before the PATCH, with a `_rollback_point` block naming the fields that PATCH changed. The restore is a live PATCH like the apply. **Write key first:** run `set -a; source ~/.advero/live.env; set +a` in the same terminal before the `MODE=live` command (`runbooks/read_only_keys.md` step 3). To put a campaign back:

```
MODE=live ALLOW_LIVE_WRITES=1 python3 changesets/instantly_phase0/apply_instantly_phase0.py \
    --apply --restore changesets/backups/phase0_<campaign_id>_<ts>.json --campaign cleaning_reactivation
```

`--restore` needs `--apply` **and** `--campaign`: it is a live PATCH, so it goes through a typed confirmation, which now comes **after** the live read. It refuses, before any request, a file that is not an unsuffixed phase0 rollback point for that campaign: a `.dryrun`, `.prerestore`, `.not_applied` or `.preapply` file, a promotion, capacity or inbox-action backup, a file from before 2026-09-22 with no `_rollback_point` block, or a point for another campaign. (A `.preapply.json` left by a run that died mid-PATCH is accepted only with `--accept-interrupted`, after you have compared it with live.) It then GETs the campaign and prints one line per field: what the restore would change, and `CHANGED SINCE THE APPLY` for any field whose live value equals neither the recorded after-image nor the before-image (someone edited it after the apply, for example a burned inbox removed by an inbox action). A field changed since the apply makes the restore refuse with exit 2 before the prompt, because putting the before-image back would undo that later change; pass `--override-later-changes` only after reading the diff and deciding the before-image should win. The override is refused together with `--yes` (a person must type the confirmation), and the `phase0.restore` Job_Log row carries `override_later_changes` and the drift lines. A drift line on `sequences` or another nested field names the path that differs (for example `sequences[0].steps[0].delay: 3 -> 5`). The after-image an apply records is what Instantly stored for the patched fields (read back from the PATCH response or a re-read), not what was sent, so a default the server adds on store is not reported as drift. Comparison is equality (`email_list` as a case-insensitive set), so live that only contains the before-image is not treated as restored. When live already equals the rollback point it sends nothing. A field the point cannot restore (missing from the before-image) makes the run exit 3 with outcome `partial`. Otherwise, after the confirmation, it reads the campaign again and refuses (exit 2, nothing sent or written) if any of the point's fields moved while the prompt was open; then it writes a `.prerestore.json` copy of what it is about to overwrite, PATCHes **only** the fields that apply changed and that differ now (never the full body, which `PATCH /campaigns` rejects as `additionalProperties: false`), verifies the result and logs `phase0.restore`. In shadow it is refused and writes nothing. If the PATCH raises, the script re-reads the campaign and says whether the restore landed; paste that into the next session.

**Exit 3 from a restore** means the restore did not end in a verified state. Two different things end that way.

**It printed `API error: ...`**: an Instantly read failed, either the first live read or the re-read after the confirmation. Both happen before the `.prerestore.json` copy and before any PATCH, so **nothing was written**. The Job_Log row is `phase0.apply` with status `api_error`, and there is no `phase0.restore` row (`apply_instantly_phase0.py:626-629`; the reads are `rollback.py:514` and `567`). **What to do:** re-run the same restore command.

**Anything else:** the `phase0.restore` Job_Log row has status `restore_failed` and its `outcome` says which case you are in (`changesets/rollback.py:552-629`):

- `restored_unverified`: the PATCH was acknowledged, but neither the PATCH response nor a re-read shows every restored field exactly equal to the rollback point. The script prints one line per field that still differs, **unless the re-read itself failed: then it prints no field lines at all** (`rollback.py:617-624`). `restored_unverified` does not mean nothing changed; the `.prerestore.json` copy of the state it overwrote was already written. **What to do:** open the campaign in the Instantly UI and compare the printed fields with the rollback point; when no field lines were printed, compare **every** field the rollback point names (its `_rollback_point` block, also printed on the restore's first `rollback point written ... fields [...]` line). Then re-run the same restore command once. If it prints `live already matches the rollback point` (exit 0, status `noop`), the restore is done. If it shows the same field as a diff again, or refuses with `CHANGED SINCE THE APPLY` on that field, Instantly is storing the value differently from what was sent: **stop, do not add `--override-later-changes`, and do not loop the restore**; paste both runs' output and the `.prerestore.json` path into the next session.
- `partial`: the rollback point has no before-image for some field, so that field cannot be put back from it. Restore that field by hand in the UI.
- `landed_after_error`, `not_restored_at_reread` or `unknown`: the PATCH raised; the re-read says whether it landed. On `not_restored_at_reread` re-run the restore once; on `unknown` check the UI first. A restore run without the write key also fails at the PATCH and ends as `not_restored_at_reread` (the reads work on the read-only key; the PATCH raises `INSTANTLY_API_KEY is not set in this process`), so check that `~/.advero/live.env` is sourced in that terminal before re-running.

Labels can be removed in the UI (Settings > Lead Labels); a label delete is not scripted on purpose.

## Thresholds

| Signal | Rule | Source |
|---|---|---|
| Variant verdict | judge A vs B only at >= 500 sends per variant; winner keeps, loser is replaced with the next opener from `openers_<niche>.md` | blueprint M3.3, `campaigns/analytics/steps` |
| Campaign verdict | no verdict before 1,000 sends; with >= 1 positive at 1,000, run to 3,000 | blueprint M4 |
| Sudden drop | any campaign or inbox whose 7-day reply rate falls below 50% of its 4-week average after the change: restore from backup, then investigate | blueprint M1 alert row |
| Bounce | > 2% on any inbox after the change: pause the inbox (A4), not the copy | blueprint M1 L3 |
| Spam words | monthly placement test >= 85% inbox; a step 3 subject that trips it gets replaced | Section 6 monthly |
| Opportunity value | `pl_value` 6000 reactivation / 7500 outbound; revisit when real deal sizes exist in GHL (S8) | offers.md |
